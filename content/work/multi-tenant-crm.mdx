## Context

Sales and service teams use the CRM to capture leads, run them through pipelines, and talk to customers by email, SMS, WhatsApp, voice and AI agents. We studied Microsoft Dynamics 365, Salesforce and Odoo, then built our own. Every company is a separate tenant, often with several branches, all sharing one deployment.

I led the architecture and a team of ten: five or more developers, three QA engineers and two business analysts. The backend grew to 170+ modules, 1,700+ REST endpoints and 350+ MongoDB schemas. The web app is a Next.js app with more than 130 pages.

## Keeping every company in its own lane

Tenant isolation is not a feature you add later. Every request knows which company it belongs to, because the login token carries it. From there, data access goes through shared pieces instead of each developer's memory:

- **Shared helpers** build the company filter and refuse to run if a company is missing, so the failure is loud, not a silent leak. They also narrow a role to its own branch or its own contacts.
- **Guards** protect the routes that need them, including a tenant guard for integrations and a guard that blocks a frozen company.
- **Tests** pin the rules, so a change that loosens one fails before release.

Background jobs and real-time events carry the company in their payloads, and each person's chat sockets join rooms for themselves, their company and the conversation, so presence and messages only reach the right people.

## Permissions from one list

Roles are sets of named permissions, such as "can edit leads". They are declared once in a registry, and a script generates the role schema and the lists the API uses from it. A check command fails if the generated files drift from the registry. We added it after a hand-kept list had left 92 flags out of sync.

Routes opt in with a decorator that names the permission they need. Plans work the same way: a decorator names the module a route belongs to, and a route outside the customer's plan answers 403 with a clear code. The frontend mirrors the same names so the UI hides what a person cannot use, but the server is the one that enforces it.

## Moving customers over

The old product and the rebuilt one had different data shapes, so customers were moved one at a time by a migration tool. It was built to be safe by default:

- It does a dry run unless told otherwise, and a real run needs an explicit flag confirming a backup exists.
- It checks that the source and target companies are the ones you meant, and that they are different.
- It moves CRM data first and recruitment data second, and refuses the second phase while live automations could re-enrol the migrated records.
- A compare tool checks the result, and a report is saved even when a run fails.

## Running it

The app runs from the same code as two processes: an API and a worker with no web server. Production is a small set of Docker services (the API, the worker, Redis and a Caddy proxy) on one server. Redis is set never to evict, and the scheduled jobs run on one worker only, because there is no leader election and a second worker would run each job twice. That constraint is written next to the config.

## The frontend

The web app is Next.js with TanStack Query for server data, Zustand for small pieces of state, and Socket.IO for real-time updates. It uses Radix and shadcn components on a shared design system with a contrast check. It is covered by Vitest unit tests and a set of Playwright end-to-end tests, and a pipeline runs type checks, lint and tests on every change.

## What I would tell another team

- Write the design document before the feature. It is cheaper to argue over a page than over a pull request.
- Put rules in shared helpers and generated files, not in each developer's memory, and make a check fail when they drift.
- Make risky tools safe by default: dry run first, an explicit flag for the real thing, and a report either way.
